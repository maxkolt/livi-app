20 ноября 2026, Москва. Исходная ревизия `d90b26768`.
Пользователь подтвердил: у 211 нет замечаний; 212 находилась на проверке около суток,

**Результат:** технические проверки доступных AAB 213 прошли. Аудит выявил конкретные
серверные проблемы и обход фильтрации клиентской телеметрии; исправления подготовлены

полное соответствие Google Play. Причина текущей задержки Google не установлена.

Production, аккаунты, данные, конфигурация авторизации и отправленный в Play AAB
не изменялись. Commit, push, публикация страниц и deployment не выполнялись.

## Исправления в рабочей копии

### P1. Проверка участников случайного звонка

`backend/routes/livekit.ts` защищал только `room_<uid>_<uid>`, но разрешал остальные
имена, включая фактически используемые `rand_room_<uid>_<uid>`. Посторонняя
авторизованная установка, знающая имя чужой комнаты, могла получить токен
публикации/подписки. Это воспроизведено на настоящей функции локально;
присоединение к чужому production-звонку не выполнялось. Эксплуатация не установлена.

Теперь оба используемых формата требуют принадлежности одному из двух участников;
неизвестные имена отклоняются. Проверка общая для HTTP и сокетного запроса токена.
Восстановление токена обоими участниками сохранено, зависимости от TTL активной пары нет.
Новые HTTP-регрессии подтверждают отказ до выпуска JWT и успешный refresh участников.
Это серверное исправление: новый AAB для его применения не нужен.

### P2. Удаление видеосообщений и превью

`backend/sockets/identity.ts` собирал для очистки файлов только image/audio из
FriendshipMessageItem. Видеокружки, существующие лишь в этой коллекции, могли
остаться доступными по прежнему URL после удаления аккаунта.

Добавлен сбор видео и `thumbUri`; `backend/utils/uploadedMedia.ts` также проверяет
оставшиеся ссылки на превью. Настоящая MongoDB и файловая интеграция подтвердила
удаление собственных mp4/jpg и сохранение пересланных файлов, используемых другим чатом.
Это также серверное исправление без пересборки AAB.

### P2. Отдельный путь Firebase-телеметрии обходил redactor

`frontend/utils/telemetry.ts` передавал native bridge исходный payload и до 500
символов `Error.message`; Kotlin отправляет их Firebase Analytics/Crashlytics.
Фильтрация logger и отдельной backend-диагностики этот путь не защищала.
Текущие явные call sites содержат идентификаторы и технические метрики;
фактическая передача текста переписки или пароля аудитом не установлена.

Теперь payload редактируется перед native bridge, а сообщение ошибки заменено
известной категорией из фиксированного списка. Произвольный текст ошибки не отправляется.
В обоих redactor исправлены camelCase/plural URI/URL-поля: mediaUri, thumbUri,
mediaUris, imageUrls и аналогичные. Тесты проверяют секреты, Bearer, URI с учётными
данными, feedback, media/data URI, циклы и сохранение обычных метрик.

Эта клиентская защита требует будущего Android-релиза. В уже собранную и отправленную
213 локальная правка не попала. Идентификаторы звонка/пользователя в обычной телеметрии
не удаляются; их нужно учитывать в Data safety. Redactor не распознаёт произвольный
личный текст в любом неизвестном будущем поле: границы payload всё равно важны.

- Backup исключает sharedpref/database/file/external; FileProvider с личными файлами

- Автомодерация **включена** в реальном Hermes 213: подтверждено дизассемблированием,

- Firebase Analytics, Crashlytics, AppMetrica, AD_ID и защищённый Google Block Store
  для ключа чата присутствуют. Утверждение «приложение вообще ничего никуда не передаёт»

Новая установка из Play, свежий физический прогон и полный Android/JVM build в этом
аудите не выполнялись. Исторические проверки S25/A35 не выдаются за текущий прогон.

## Что ещё требует работы или проверки Console

1. **UGC:** в текущих исходниках не найдено принятия правил до создания пользовательского
   контента или отдельной блокировки пользователя для дружеских чатов 1:1. Report
   текущего random partner с pair-block не покрывает все дружеские взаимодействия.
   Это существовавшие ранее риски по [UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en).
   Автоматически новый onboarding и новую систему block этот аудит не добавляет.
2. **Console:** проверить Data safety, Advertising ID, Child Safety,
   [Restrict Minor Access](https://support.google.com/googleplay/android-developer/answer/16302250?hl=en),
   FGS phoneCall/microphone/mediaPlayback/specialUse, full-screen intent и App access.
   По репозиторию нельзя подтвердить отправленные ответы или замечания Google.
3. **Приватность вложений:** обладатель URL по-прежнему может читать файл; E2EE для
   всех вложений не реализовано. Загрузки без отправленного сообщения не привязаны
   к владельцу. CallTimeline хранится по TTL 30 дней и не очищается в wipeMe;
   исключения хранения нужно согласовать с обещаниями политики удаления.
4. **Старые установки:** совместимость legacy не равна завершённому включению строгой
   защиты. Нельзя выполнять прежний план массового сброса или менять поколение
   аккаунтов автоматически в рамках этого аудита.

## Срок проверки Google

По [официальной инструкции Google](https://support.google.com/googleplay/android-developer/answer/9859654?hl=en)
проверка может занимать от нескольких часов до семи дней и дольше в отдельных случаях.
Время считается от последнего отправленного изменения; дополнительная отправка
во время review может вернуть приложение в конец очереди. Замена 212 на 213 поэтому
могла продлить ожидание. Это возможное объяснение, а не установленная причина.
Двое суток сами по себе не доказывают нарушение. Решение по конкретной 213 зависит
от Play Console и проверки Google; гарантировать одобрение этим аудитом нельзя.
