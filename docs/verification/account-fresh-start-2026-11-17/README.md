Обновление 18.11.2026: [подготовительный backend развернут и создана предварительная резервная копия](../security-release-ready-2026-11-18/README.md).
Production-сброс и строгий новый старт всё ещё не активированы; ниже сохранены результаты первоначальной подготовки.

Согласовано: вместо переноса старых аккаунтов подготовить создание новых. Потеря старых данных допустима. Пользователь разрешил сброс только тестового LiVi Dev на A35 для проверки; рабочая база на этом этапе не очищается. AAB пользователь собирает сам. Ни этот документ, ни подготовленные скрипты не означают, что production уже сброшен или обновлён.

## Поведение приложения

Существующий экран создания профиля остаётся прежним. Телефон/почта/пароль не добавлены. Новая установка получает случайный идентификатор и 256-битный секрет в SecureStore; сохранённые установки не меняются без подтверждённого сброса. Переустановка без сохранённых учётных данных создаёт новую установку, а не пытается восстановить чужую/старую привязку через Android ID.

Публичный `/api/app-settings` публикует `accountDataGeneration` только после настройки `ACCOUNT_DATA_GENERATION` при согласованном сбросе. Значение — публичный неизменяемый идентификатор операции, не пароль. Обычный релиз не меняет его. Ответ не кэшируется.

При отличающемся маркере и наличии старых локальных данных старт приложения и авторизованные Socket.IO-запросы ждут экрана «Новый старт LiVi». После нажатия «Создать новый профиль» очищаются локальная история, профиль, очереди, оформление и старые учётные данные; сохраняется выбор языка. Удаляется ключ старого профиля из SecureStore/native vault; Android очищает входящие inbox, счётчики, уведомления и сохранённые credentials звонков. Новая регистрация получает пустой профиль. Клиент не отправляет прежний профиль для восстановления.

Запись о начатом сбросе сохраняется до очистки. При ошибке хранения приложение остаётся на экране повтора. После прерывания процесса подтверждённая операция завершается при следующем запуске; маркер принятой версии данных записывается последним. Отсутствие сети, HTTP 401 и отсутствие маркера на старом сервере не разрешают удалять локальные данные.

После включения маркера старый клиент без его подтверждения не может вызвать `identity:attach`, включая создание нового аккаунта. Сервер возвращает `account_reset_required`. Это ограничение совместимости; сам публичный маркер не является доказательством владения. Доступ к новым аккаунтам требует оригинального секрета.

## Состав очистки MongoDB

Скрипт `backend/scripts/reset-accounts.cjs` по умолчанию делает только инвентаризацию. Отдельный apply требует точного имени БД и маркера, остановленного `livi-backend`, строгой конфигурации, резервного архива и успешного чтения архива через `mongorestore --dryRun`. URI передаётся Mongo tools через временный файл 0600, не через аргументы. Записи пользователей не выводятся.

Удаляются записи из:

```
users, installs, messages, offlinemessages,
friendshipmessages, friendshipmessageitems, friendship_edges,
pushtokens, missed_calls, call_timelines, userreports,
fliq_user_state, installmigrationproofs,
release_diagnostics, release_diagnostic_reports,
cosmetic_purchases, intellectmoney_cosmetic_purchases
```

Сохраняются `appconfig`, `fliq_videos`, `fliq_collect_state`: настройки выпуска, общий каталог роликов и бюджет/состояние сборщика. В `appconfig` добавляется квитанция `accountDataGeneration`. Повтор той же операции запрещён, чтобы не удалить уже новые аккаунты. Неизвестная коллекция блокирует apply до отдельного разбора. Удаление записей и запись квитанции выполняются в одной MongoDB-транзакции; standalone Mongo без replica set не подходит. Индексы не удаляются.

## Порядок production-переключения

1. Проверить публикуемый AAB 212, дождаться его доступности в Google Play. QA APK не является публикацией. Пользователям старых сборок понадобится обновление. Убедиться, что AAB 212 ранее не использован в Play; иначе выбрать следующий versionCode до сборки.
2. Выполнить read-only инвентаризацию нужной БД: `node scripts/reset-accounts.cjs --database <имя-БД>`. Проверить неизвестные коллекции, размеры загруженных файлов и Redis namespace. Показать итоговый состав удаления пользователю и получить финальное подтверждение именно production-очистки.
3. Подготовить backend из проверенного коммита с backup/rollback, не менять действующие ключи/pepper. Проверить отсутствие звонков/SFU participants/очередей, остановить `livi-backend`, заблокировать автоматический restart на время обслуживания. Другие писатели этой БД также должны быть остановлены.
4. Сохранить `.env` и резервную копию Redis; подготовить закрытый каталог резервных архивов. В конфигурации нового сервера отключить `legacy-migration`, установить `HTTP_INSTALL_SECRET_REQUIRED=1` и выбрать неизменяемый `ACCOUNT_DATA_GENERATION` (например `fresh_20261117_1`). Не запускать сервер до окончания сброса.
5. Запустить apply с точным `<имя-БД>:<маркер>`, абсолютным `--backup-dir` и `--generation`. Скрипт сам создаёт полный архив Mongo и проверяет его чтение перед транзакцией. `--dryRun` Mongo tools проверяет чтение архива, но не заменяет пробное восстановление в отдельную БД.
6. При остановленном backend удалить только ключи принадлежащего LiVi namespace `livi:*` через SCAN/UNLINK. Не применять FLUSHALL/FLUSHDB к общей Redis. Ключи включают старые unread, viewing, очередь, пары, call state и rate limits. Проверить отсутствие других активных экземпляров backend.
7. Убрать пользовательские media из обслуживаемого каталога `public/uploads/media` в закрытый резервный каталог вне public; оставить каталог и правильные права для новых загрузок. Старые URL должны перестать выдавать файлы. Не удалять статические ресурсы приложения/сайта. Путь и состав перемещения предварительно сверяются на сервере; Mongo-скрипт файловую систему сервера не очищает.
8. Запустить новый backend, сверить source/dist и `.env`, health/Mongo/Redis/adapter, строгую авторизацию и маркер. Проверить новое создание профиля, повторный запуск того же аккаунта, запрет запросов без секрета, старые ссылки на media, отсутствие старых уведомлений/очередей.
9. После публикации выставить latest-app-version. Откат исполняемого кода не должен возвращать старую совместимость или менять маркер. После регистрации новых пользователей восстановление старой БД требует отдельного решения: оно удалит новые данные.

## Проверки

Автоматические и физические результаты записываются рядом после завершения. Тестовые БД имеют собственные имена, используют локальный replica set на 27029 и синтетические ключи. Production `.env` в них не загружается.

Сценарий `npm run test:fresh-start` в backend проверяет полный собранный сервер до/после очистки: сохранение настроек, публичный маркер, отказ старому клиенту, создание нового пустого профиля с хэшем секрета, HTTP-проверку секрета и запрет подмены нового аккаунта.

Этот переход не добавляет вход на другом телефоне/восстановление по почте и не закрывает отдельные замечания о PiP, Bluetooth и медиапроверках.
