# Skia и Fliq: повторная проверка двух устройств

24 ноября 2026, dev-сборка `com.kolt12max.livi.dev`, 215 / 1.1.24. Итог относится к повторному прогону после сообщения пользователя о ручных переключениях на телефонах. [Машиночитаемые результаты](./skia-device-checks.json) содержат ответы, PID, временные метки поздних ответов и состояния Fliq.

| Samsung S25 Ultra, SM-S938B, R5GL550T4TB | 16 | VPN «Привата», com.privatasolutions.vpn | 13116 |

SHA-256 установленного APK совпал на обоих устройствах с локальным артефактом: `f57baa87ab410d1d9bbeef1a5bb7d7461848c734df911b0bb3ceba25d25efe76`. VPN проверен по подключённому NetworkAgentInfo, а не значку: на A35 активного VPN нет; на S25 сеть Приваты охватывает UID приложения. VPN на A35 не включался.

## Загрузки и снимки

На каждом устройстве прошли 14 проверок: обычный/медленный успешный ответ, HTTP 404/503, пустое тело, повреждённая картинка, оборванное тело, отсутствие ответа сервера, неверный URI, отсутствующие Canvas/View, успешный снимок живого Canvas, снимок текстового View и безопасный отказ сложного View. Всего 28 проверок.

Таймаут сервера без ответа завершился reject через 15011 мс на A35 и 15005 мс на S25. Повреждённые байты не превратились в изображение: декодер вернул null. Canvas и текстовый View дали изображения с положительными размерами.

Для управляемых ответов использовался локальный HTTP-сервер через USB/adb reverse. Это проверяет настоящий Android-загрузчик и JNI, но эти пакеты не являются проверкой маршрута через удалённый VPN-сервер. Внешний YouTube-запрос проверен отдельно ниже.

## Reload и поздние ответы

На каждом телефоне выполнены три reload. Перед каждым сервер принимал два запроса и удерживал ответы. Ответы 200 и 503 выпускались только после готовности нового runtime; временные метки подтверждают именно этот порядок. Всего 6 reload и 12 поздних ответов. После каждого цикла свежая загрузка работала, результаты старого runtime в новом состоянии не появлялись, PID сохранялся.

Перед каждым reload дополнительно ставились в очередь восемь асинхронных снимков Canvas, всего 48. Это нагрузка рядом с teardown; утверждения, что каждый такой снимок завершался именно после teardown, не делается. Для HTTP-запросов задержка до нового runtime обеспечена серверным барьером.

## Fliq и владение изображениями

На обоих телефонах прошли проверки реального дерева компонентов и нативные свайпы:

- Пять свайпов на устройство; в проверяемых состояниях после перехода back равен null. Индексы A35: 1, 2, 3, 4, 4; S25: 1, 2, 3, 4, 5.
- При запросе 30 предзагрузок наблюдавшиеся максимумы на каждом телефоне: две активные загрузки, восемь pending, шесть записей, 6291456 байт по оценке RGBA.
- После `am send-trim-memory ... RUNNING_LOW` кэш пуст, а используемое изображение остаётся валидным и доступным Canvas. Принудительного dispose общего изображения не было.
- После ухода на Поиск поддерево ActiveFliqAmbient отсутствует, URL null. Наблюдавшееся освобождение при проверке: 1888 мс на A35, 1765 мс на S25.
- С сокращённым только для теста дедлайном 250 мс и ответом сервера через 2200 мс pending очищался, две нативные операции продолжали занимать свои слоты. Поздние данные не попадали в кэш, оба callback получили null ровно по одному разу; после завершения active стал равен нулю.
- Уход приложения в фон освобождал поддерево изображений. После возврата свет загружался снова; PID не менялся.

Для воспроизводимой проверки переходов/кэша использовались контролируемые PNG через тот же `Skia.Data.fromURI` и production-декодер. На A35 они включались до открытия Fliq, чтобы недоступность внешнего превью не блокировала проверку владения. На S25 сначала проверено реальное превью, затем контролируемые данные. Эти временные подмены выполнены только в тестовом runtime и восстановлены в finally; исходники приложения для них не менялись.

Реальный `https://i.ytimg.com/.../hqdefault.jpg` на S25 с Приватой загрузился за 1175 мс, изображение 480×360. На A35 без VPN отдельный внешний запрос на момент финальной проверки оставался pending; на экране был индикатор загрузки и штатное сообщение об ограниченном доступе к YouTube. Полная работа YouTube без VPN этим прогоном не подтверждена. Проигрывание/слышимость звука не являлись предметом проверки Skia.

## Найденное дополнительное исправление

В первом физическом прогоне обнаружен native SIGABRT при снимке корневого View на обоих телефонах. Причина по Java-логу: `Software rendering doesn't support RuntimeShader`; исключение выходило через `JniPlatformContext::takeScreenshotFromViewTag` без перехвата.

Патч дополнен границей обработки Java/JNI-ошибок, проверками null/размеров/результатов AndroidBitmap, владением local_ref и RAII-разблокировкой пикселей. Java-служба логирует ожидаемый отказ отсутствующего/неподдерживаемого View вместо вызова фатального обработчика ReactContext. После пересборки и установки на оба телефона тот же корневой View возвращал reject без завершения процесса; обычные снимки работали. Поддержка программного снимка RuntimeShader не добавлялась.

## Итог и ограничения

В чистом повторном прогоне новых native crash нет: ApplicationExitInfo до/после не содержит новых записей reason=5, PID совпадают во всех циклах и проверках Fliq. После тестов подтверждены production-загрузчик, отсутствие тестового таймаута, отсутствие активного поддерева Fliq и пустой кэш. Временные настройки тестов восстановлены; на A35 VPN выключен, Привата на S25 остаётся включённой.

В более раннем прогоне, который пересекался с ручным удалением задач из недавних, на S25 зарегистрирован ещё один SIGABRT в `libexpo-modules-core.so`, `expo::LazyObject::get`, PID 10715, 19:56:31. Его связь со Skia не установлена; отдельное расследование этого старта не выполнено. В чистом повторе он не воспроизвёлся. Поэтому этот отчёт подтверждает перечисленные сценарии Skia/Fliq, а не отсутствие всех возможных падений приложения.

Release/AAB с исправлением и длительный профиль native/GPU RAM не проверялись. Signed AAB 215 до патча остаётся прежним.

Полные локальные доказательства, скриншоты и копии драйверов: `/private/tmp/livi-skia-two-device-20261124/recheck/`. Исходные дампы найденных ошибок сохранены уровнем выше. Скрипты хранят конфигурацию текущего рабочего места и используют внутренние состояния dev-сборки; это не публичный API приложения.
