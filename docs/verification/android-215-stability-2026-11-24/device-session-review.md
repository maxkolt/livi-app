## Мерцание логотипа после принятия входящего

Пользователь уточнил: мерцает логотип камеры, а не видеопоток; происходит после принятия входящего звонка.

На A35 подтверждён лишний переход native → Main → повторный startActivity(Main) из JS:

- 17:06:57.148: IncomingCallActivity передаёт принятие JS и выводит Main.
- 17:06:57.172: первый bringMainToFrontImmediate успешно запускает Main.
- 17:06:57.260: Main уже resumed.
- 17:06:59.509: второй bringMainToFrontImmediate опять вызывает startActivity, хотя Main уже впереди.
- 17:06:59.609–17:06:59.631: лишний pause/resume того же экземпляра Main.

В LiviAppModule.bringMainToFrontImmediate добавлена проверка на UI-потоке: уже находящийся впереди полноэкранный Main не запускается повторно, крышка принятия заново не вооружается. Первый вывод фонового Main и возврат из настоящего PiP остаются разрешёнными. API PiP проверяется только на Android 8+.

Сам источник каждого кадра логотипа по UID-логам не установлен: это может быть системный starting window/снимок задачи либо другой визуальный слой перехода. Подтверждён лишний lifecycle-переход, который исправлен в коде; окончательная приёмка отсутствия мерцания требует повторного принятия звонка с записью экрана. Нельзя считать эту визуальную ошибку полностью устранённой только по сборке и тестам.

Тема обычного запуска и уведомлений не менялась. Вызовы answer уже передавали SPLASH_SCREEN_STYLE_SOLID_COLOR; [AOSP Android 16](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/wm/ActivityRecord.java) проверяет этот явный вариант раньше icon_preferred. Поэтому наличие icon_preferred само по себе не объявлено причиной и не удалялось.

## Уточнение перехода после повторной проверки обоих устройств

Пользователь потребовал: принимающий после Accept переходит с native incoming в аудиозвонок, инициатор после принятия — с native outgoing в аудиозвонок. Допустим однотонный фон, пока интерфейс ещё не готов; ждать подключения комнаты/медиа после готовности интерфейса нельзя.

Новая запись A35 `answer-flash-after.mp4` также содержит логотип: кадр 0567 (56.7 с) между пустыми кадрами 0566/0568. В системном журнале 17:53:48.188 зафиксирован возврат Main, 17:53:48.211–48.474 — отдельное окно `Splash Screen`. Это подтверждает системную поверхность при повторном показе работающей задачи. Причина повторного выбора иконки установлена по совокупности записи, темы и пути AOSP; отдельная трассировка внутреннего состояния Samsung WindowManager не выполнялась.

В Android 16 `ActivityTaskSupervisor.findTaskToMoveToFront` вызывает `r.showStartingWindow(true)` без передачи текущих ActivityOptions; выбор стиля в ActivityRecord затем может опираться на общую тему. Поэтому ранее заданный явный SOLID_COLOR не гарантировал отсутствие логотипа. Убрано глобальное icon_preferred в API33+ теме. Все основные запуски incoming из JS/native FCM/FGS и пять call PendingIntents явно используют SOLID_COLOR, чтобы возвращаемый Main мог наследовать однотонный стиль. Параметр ICON у нативных message/missed PendingIntents и drawable обычного сплэша сохранены. Отдельная физическая регрессия холодного запуска/уведомлений в этой итерации ещё не выполнена.

Источники: [AOSP ActivityTaskSupervisor Android 16](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/wm/ActivityTaskSupervisor.java), [AOSP ActivityRecord Android 16](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/wm/ActivityRecord.java).

Убрана отдельная JS-крышка IncomingAnswerConnectingCover с заблокированными кнопками. MainActivity наблюдает за настоящим native View VideoCall с идентификатором текущего callId и снимает однотонный фон после двух готовых native-кадров. Устаревшие callback другого поколения не снимают фон нового звонка; listener очищается при уничтожении Activity. Проверка не ждёт сетевого статуса. JS guard завершается microtask после UI layout вместо двух requestAnimationFrame, которые в предыдущем вызове задерживали снятие крышки ещё примерно на 3 секунды после layout. Пока UI не готов, фон остаётся допустимой защитой от показа Home.

В A35 crash-буфере также зафиксирована ошибка 18:06:30 `showIncomingAnswerNativeCover got 1 arguments, expected 0`: во время Fast Refresh новые JS-аргументы попали в ещё прежний APK. Новую проверку необходимо проводить после завершения установки/запуска обоих APK, без изменений исходников, переустановки и открытия dev-ссылок во время звонков.
