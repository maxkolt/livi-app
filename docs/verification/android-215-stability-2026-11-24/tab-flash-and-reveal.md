# Повторная приёмка: вкладка A35, резкость и задержка

24 ноября 2026. Пользователь после прогона сообщил о короткой вспышке прежней вкладки на принимающем A35, резком переходе обоих устройств и сохранившейся задержке. Эта обратная связь означает, что предыдущая итерация не принята как завершённое исправление.

Логи: `/private/tmp/livi-215-final-session-20261124/tab-flash-recheck`; MP4 обоих устройств: `caller-delay-videos`. Приложения во время прогона не перезапускались. Видео завершены и сохранены; длительный сбор UID-logcat и памяти продолжается.

## Новые измерения

- A35 принимает: native Accept 18:25:53.128, начало UI-крышки 53.215, старый native gate объявил View готовым 54.926, подтверждение авторизации 55.860, emit accept 55.862, JS onLayout 56.127.
- S25 принимает: native Accept 18:26:13.857, accept emit 13.886 — 29 мс после кнопки. Подтверждение приходит инициатору A35 в 13.924, но native outgoing снимается только в 15.385; старый gate считает экран готовым в 17.353, JS onLayout в 18.636.

Таким образом, fast path из предыдущей итерации действительно сработал на S25, но срок кеша 6 с вновь заставил A35 ждать reauth. У инициатора по-прежнему есть задержка обработки UI после получения подтверждения; она не объясняется только доставкой события.

В записи A35 дополнительно извлечены все 60 реально закодированных кадров участка 42–48 с. Их интервалы неравномерны; некоторые кадры разделены сотнями миллисекунд. Просмотренные кадры показывают native incoming, сплошной фон и затем audio UI. Мелькание вкладки, о котором сообщил пользователь, по этим кадрам пока не локализовано; отсутствие такого кадра в записи не опровергает наблюдение пользователя. Старый gate проверял только attached/shown/size два кадра подряд, что не доказывает реальное рисование верхнего экрана native-stack.

## Новая правка

1. Внешняя граница VideoCall на Android — `LiviCallContent`, наследник ReactViewGroup. Native подтверждает готовность только после dispatchDraw настоящего поддерева, с проверкой верхнего Screen в ScreenStack, видимости и alpha предков.
2. Однотонный фон раскрывается на следующем native-кадре за 140 мс. Проверки callId и поколения сохраняются; повторный show отменяет старую анимацию, cleanup отменяет её при завершении. Layout/геометрия теперь только запрашивают invalidate, а не снимают фон.
3. Синхронная часть входящего ответа и обработчик call:accepted объединены через unstable_batchedUpdates: промежуточные состояния Home не требуют отдельных React commits до навигации.
4. Для call:accept используется подтверждённая сервером привязка того же живого socket ID к тому же user ID. Она не становится гостевой только из-за истечения 6 с кеша. Смена соединения/пользователя, disconnect и сброс успешной авторизации запрещают быстрый путь. Ответ сервера unauthorized/forbidden/callee_socket_not_found вызывает forced reauth и один повтор.
5. Серверная проверка участника не изменена: backend/index.ts в call:accept сравнивает sock.data.userId с получателем link.b до принятия, затем проверяет обязательные E2EE declarations. Срок freshness 6 с сохранён для остальных privileged операций; он отделён от срока существования привязки живого соединения. Изменение касается клиентского порядка запросов, не ослабляет серверную проверку и не отключает шифрование.

Новый алгоритм раскрытия требует повторной физической приёмки. Тесты и сборка подтверждают корректность проверяемых веток, но не устанавливают отсутствие мелькания/задержки после правки на телефонах.

## Автоматические проверки новой итерации

179 frontend suites / 1710 tests PASS, TypeScript и ESLint PASS; 7 native suites / 23 tests PASS, dev APK собран. В новых тестах зафиксировано, что живая серверная привязка не теряется после 6 с freshness, но не переживает смену пользователя/соединения или disconnect; отказ сервера forbidden принудительно запускает reauth перед повтором accept. Эти тесты не проверяют визуальную плавность на физических телефонах.

Граница native draw повторно запрашивает отрисовку только пока ожидается текущий callId: это учитывает случай, когда Android уже закешировал display list View, а фрагмент стал верхним позже. После начала раскрытия цикл прекращается. Отложенный callback дополнительно сверяет текущий callId самой View, а не только Activity.

Защитный фон также поглощает нажатия, пока готовится экран звонка: повторный тап не может нажать кнопку прежней вкладки под ним. После подтверждённого draw, с начала плавного раскрытия, ввод получает настоящий экран звонка.
