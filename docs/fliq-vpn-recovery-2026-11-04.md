# Fliq: восстановление воспроизведения через VPN

Проверка 4 ноября 2026 года, начиная с 20:04 МСК. Устройство: Samsung A35 SM-A356E
(`RFCX306PWLE`), Android 16 / API 36. VPN: HIRO, сервер «Австрия».
По уточнению пользователя воспроизведение без VPN не является условием приёмки.

## Исправления

- Ошибка YouTube больше не перелистывает ленту через 700 мс. Недоступное видео остаётся
  с действиями «Повторить» и «Следующее»; сетевые/медийные ошибки восстанавливают текущий ролик.
- Восстановление отслеживает движение времени видео после первого кадра, включая случай,
  когда iframe продолжает сообщать PLAYING при замершем времени. Повторная загрузка
  сохраняет позицию, звук и режим воспроизведения. Поздние сообщения старого WebView игнорируются.
- Автоматические попытки ограничены: ожидание 12, 20 и 30 секунд; затем ещё 30 секунд
  на последнюю загрузку и доступен ручной повтор. Возврат сети запускает восстановление
  зависшего видео, а исправно играющее видео не перезагружается из-за уведомлений NetInfo.
- Временная буферизация, ошибка и сброс времени после смены сети не считаются концом видео.
- Соседние WebView создаются после первого кадра текущего видео. Их медиаподгрузка
  приостанавливается при буферизации текущего; второй сосед ждёт завершения подгрузки первого.
- Уход в VPN-приложение больше не превращается в ручную паузу. Явная пауза человека сохраняется.

Ошибка IFrame API 5 относится к HTML5-плееру и обрабатывается как восстанавливаемый сбой.
Описание кодов: [официальная документация YouTube](https://developers.google.com/youtube/iframe_api_reference#onError).

## Физический телефон

Проверялись одновременно IFrame API и настоящий `<video>` внутри YouTube iframe через CDP:
время, `paused`, `readyState` и `getVideoPlaybackQuality().totalVideoFrames`.
Счётчик PLAYING сам по себе не принимался за доказательство воспроизведения.

| Сценарий | Наблюдение |
| --- | --- |
| Просмотр через VPN | `cFuAhaj4rJg`: 2,80 → 27,42 с, декодированные кадры 164 → 903; видео играет. |
| Автопереход | Переходы `VDgRcEhM7XY` → `cFuAhaj4rJg` → `wbyvMRLq-TI` произошли после окончания видео. |
| Ручная пауза и возврат из VPN-приложения | `wbyvMRLq-TI` остаётся на 8,319748 с, `paused=true`, 331 кадр. После явного продолжения время и кадры растут. |
| Переподключение VPN | Туннель отключён и вновь подключён, проверено через `dumpsys vpn_management`. Тот же `wbyvMRLq-TI` продолжился с 11,60 с до 22,70 с; затем нормальный переход к следующему. |
| Приоритет текущего видео при первом входе | После ограничения соседних WebView первый кадр получен за 11,114 с; следующий подготовленный ролик стартовал за 185 мс. Это отдельные замеры, не гарантия скорости любого VPN. |
| Принудительное зависание iframe | Через CDP временно заблокирован `playVideo` и вызван `pauseVideo`, без ручного hold. `gwmMsy_s0i0` застыл на 35,385481 с; через ~12 с пересоздан WebView того же видео; ещё через ~6 с появились кадры. Затем 37,95 → 52,52 с, кадры 142 → 506. |

Принудительное вмешательство исчезло вместе со старым WebView; в код приложения оно не добавлялось.
В итоговом прогоне также подтверждено воспроизведение `gwmMsy_s0i0` до искусственного сбоя:
время 1,98 → 27,62 с и кадры 53 → 694.

Артефакты этой сессии: `/private/tmp/livi-fliq-20261104/` — журналы тестов и сборки,
`fliq-device.log`, `vpn-playback.jsonl`, `manual-pause*.jsonl`, `vpn-reconnect.jsonl`,
`final-cold-start.jsonl`, `forced-stall.jsonl`.

## Границы проверки

Проверен один физический телефон и один VPN-провайдер/сервер. Холодная загрузка YouTube
по-прежнему зависит от доступности и скорости туннеля; мгновенный старт не гарантируется.
Человеческая слышимость звука в этом прогоне не проверялась. Публикация в Google Play,
коммит и push не выполнялись.
