# Отладка пушей входящего звонка в релизе

Когда получателю звонка не приходит уведомление (ни на заблокированном экране, ни поверх другого приложения).

## 1. Подготовка

- Телефон с **релизной** сборкой LiVi подключён к Mac по USB.
- На телефоне включена **отладка по USB** (Настройки → Для разработчиков → Отладка по USB).
- На Mac установлен `adb`: `brew install android-platform-tools` (если нет).

## 2. Захват логов на телефоне (получатель)

В терминале из папки `frontend`:

```bash
chmod +x scripts/capture-push-logs.sh
./scripts/capture-push-logs.sh
```

Скрипт очистит logcat и начнёт писать логи в файл `livi-push-debug-YYYYMMDD-HHMMSS.log` в текущей папке.

## 3. Воспроизведение

1. **Не останавливая скрипт**: на телефоне открой LiVi, затем сверни приложение (Home) или закрой из списка задач.
2. С **другого устройства** (или второго аккаунта) позвони этому пользователю (видеозвонок другу).
3. Подожди 10–15 секунд (звонок идёт, пуш должен уйти).
4. В терминале на Mac нажми **Ctrl+C** — запись логов остановится.

Логи сохранятся в `frontend/livi-push-debug-*.log` (и отфильтрованная копия в `livi-push-filtered-*.log`).

## 4. Что смотреть в логах

### На устройстве (получатель)

- **FCM/FirebaseMessaging** — доставка пуша на устройство. Если есть запись о получении сообщения в момент звонка — пуш до телефона дошёл, проблема в отображении/канале. Если записей нет — пуш до устройства не доходит (токен, сеть, backend).
- **ReactNativeJS** — логи из JS (наш `logger`). В релизе `EXPO_PUBLIC_LOG_LEVEL=warn`, поэтому видны только `[WARN]` и `[ERROR]`; строки с `[push]` могут быть только при ошибках (например, регистрация токена, обработка ответа).
- **expo / notification** — если expo-notifications что-то пишет в logcat при получении пуша.

### На backend (обязательно проверить)

Убедись, что при звонке **backend реально отправляет пуш**:

- В логах сервера при `call:initiate` должна быть отправка в Expo Push (без ошибок). Например, поиск по логам: `call:initiate`, `sendPushToUser`, `push`, `push-test`, ошибки от Expo/FCM.
- Если backend логирует ошибки при отправке пуша (invalid token, network, etc.) — причина на стороне сервера/токена.

Проверка на сервере (если есть доступ к логам):

```bash
# пример: смотреть логи сервиса в момент звонка
journalctl -u livi-backend -f | grep -E "call:initiate|push|sendPushToUser|Expo"
```

## 5. Типичные причины

| Симптом в логах | Возможная причина |
|-----------------|-------------------|
| Нет записей FCM о получении сообщения в момент звонка | Пуш не доходит до устройства: неверный/устаревший FCM-токен, backend не шлёт пуш, ошибка Expo Push API. Проверить backend-логи и что токен получателя актуален. |
| FCM сообщение есть, уведомления нет | Канал уведомлений «Звонки» отключён или заглушен пользователем; ограничения батареи/энергосбережения для приложения. |
| В backend ошибка при отправке пуша | Проверить FCM/Expo креды, формат payload, что для пользователя есть сохранённый push-токен в БД. |

## 6. Быстрая проверка без скрипта

Ручной захват в момент воспроизведения:

```bash
adb logcat -c && adb logcat -v time 2>&1 | tee livi-push-manual.log
```

Воспроизвести сценарий (свернуть приложение → звонок), затем Ctrl+C и поиск в `livi-push-manual.log` по словам: `FirebaseMessaging`, `FCM`, `push`, `notification`, `ReactNativeJS`, `[push]`.

## 7. Кнопки «Поднять» / «Отменить» на Android

Категория `incoming_call` с действиями «Поднять» и «Отменить» регистрируется при старте приложения. Backend отправляет `categoryId: 'incoming_call'` и дублирует его в `data` (для Android expo-notifications читает categoryId из `remoteMessage.data`).

На Android кнопки действий часто видны только в **развёрнутом** уведомлении: потяни шторку вниз и разверни уведомление о звонке — там должны появиться «Поднять» и «Отменить». В компактном heads-up они могут не отображаться.

## 8. Полноэкранный входящий звонок (full-screen intent)

Чтобы получатель видел **полноэкранный** экран входящего звонка (как на скриншоте: имя звонящего, «Входящий вызов», кнопки «Отклонить» / «Ответить») даже когда приложение в фоне или экран заблокирован, используется **Full-Screen Intent** на Android (API 29+).

Что уже сделано:

- В **AndroidManifest** есть разрешение `USE_FULL_SCREEN_INTENT` и у MainActivity — `showWhenLocked="true"`, `turnScreenOn="true"`.
- В проекте применён **патч** к `expo-notifications` (`frontend/patches/expo-notifications+0.31.4.patch`): для уведомлений с категорией `incoming_call` к уведомлению добавляется `setFullScreenIntent()`. При приходе пуша о звонке система может показать полноэкранный экран и запустить приложение по нажатию.
- После `npm install` в папке `frontend` патч применяется скриптом `postinstall` (команда `patch`).

Важно:

- На части устройств пользователь должен вручную разрешить приложению показывать полноэкранные уведомления: **Настройки → Приложения → LiVi → Уведомления → Входящие звонки** (или «Звонки») → включить опцию вроде «Показывать на экране блокировки» / «Full screen».
- При открытии приложения по full-screen intent срабатывает тот же механизм, что и при тапе по уведомлению: `getLastNotificationResponseAsync` и навигация на экран входящего звонка.

## 9. Dev-версия: уведомление не приходит

Если в dev-сборке токены регистрируются (`[push] token register response ok`), но при звонке на домашнем экране получателя уведомление не появляется:

1. **Backend в момент звонка**  
   В логах сервера при `call:initiate` должны быть строки:
   - `[call:initiate] sending call push to recipient` с `peerId` (userId получателя)
   - `[push] sendPushToUser: sending` с `userId`, `kind: 'call'`, `tokenCount: 1` (или больше)  
   Если вместо этого есть `[push] sendPushToUser: no tokens for user` — у получателя нет токена в БД (другой backend/БД или токен не зарегистрирован для этого userId).

2. **Один и тот же backend**  
   Оба устройства (звонящий и получатель) должны ходить на один и тот же `EXPO_PUBLIC_SERVER_URL_ANDROID` (или `EXPO_PUBLIC_SERVER_URL`). Иначе токен получателя сохраняется на одном сервере, а пуш при звонке уходит с другого — токенов для получателя не будет.

3. **Настройки уведомлений на телефоне получателя**  
   Настройки → Приложения → LiVi Dev → Уведомления: включены. Канал «Звонки» (Calls) не заглушен. Энергосбережение/оптимизация батареи для LiVi Dev не должна убивать фоновую доставку.

4. **Проверка на релизной сборке**  
   Собери и установи релизный AAB/APK (тот же проект, с FCM). Если в релизе уведомление приходит, а в dev — нет, возможны отличия в FCM/проекте или в том, как система обрабатывает уведомления от dev-сборки.
